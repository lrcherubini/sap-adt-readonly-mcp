# The tools

What each tool answers, and the guard rails it holds: what it reads, how it pages, what it
refuses and which traps of the ADT it avoids (each measured in
[`adt-api-reference.md`](adt-api-reference.md)). Every answer follows the completeness
contract of the README (*Complete or not, in fields*). How to install and register the server
is in the [README](../README.md).

Times are ISO 8601. A time with `Z` is UTC; one without an offset is the system's local clock,
where the ADT writes local time or its zone is not measured. A dump is named by its short ST22
key (`id`), the value `adt_runtime_errors` takes in `detail`.


| Tool | What it answers | Guard rails |
|---|---|---|
| `adt_search` | Which objects match this name pattern? | `max` 50 by default, up to 999. An answer of exactly `max` hits is `complete: false` with `incomplete: [{code: "SERVER_PAGE_FULL"}]` and `narrowBy` (the arguments that reduce it) — the quick search has no paging, so a full page is not proof of a complete list. Hits of another subtype of the facet asked are left out and counted (`outsideFacet`). ⚠️ An empty answer is not proof of absence either: the search does not see every object that exists (a generated include, measured); the by-name tools fall back to the direct URI for `PROG/P`, `PROG/I`, `CLAS/OC`, `FUGR/F` and say `foundBy: "uri"` when that is how they got there. With a facet given, an empty answer is asked once more through the `quickSearch` route, which sends the facet **whole** (the client library strips it — `FUGR/FF` is only ever found this way); that reply carries no description, and the answer says `foundBy: "facet"`. For an application log object (`APLO`) or a check variant (`CHKV`) the answer also carries `legacy`: the ones created in SLG0 (`BALOBJ` rows without a `TADIR` `R3TR APLO`) or in transaction SCI (`SCICHKV_HD` rows that are not `CHKV`), which the ADT does not publish, read through the data preview with the search pattern as a `LIKE`. Each comes with its text, check variants as `global` or `local` (never with their owner), plus `guidance` on where it lives and how to work with it. `complete: false` with an `incomplete` code (`CAP_REACHED`, `NOT_READ`) when a read was capped or failed (`LEGACY_OBJECTS_NOT_READ`) |
| `adt_read_source` | What is the real source in the system? — and, with `enhancements: true`, what customer code is implanted in it | the source is the text answer and `source` in the structured content (a client shows one or the other); next to it, what was asked, read and left out (`complete`, `incomplete`, `enhancements: {asked, read, count}`, `textElements`, `version.exists`, `alternatives`); class includes selectable; enhancement source only when asked for. `objectNames: [...]` (max 25) reads a batch, one JSON item per name, a failed name never stops the others (`BATCH_ITEM_NOT_READ`); a name that resolves to nothing is counted as `notFound`, an answer and not a gap. An ENHO has no source at its own URI (measured): the answer names the **enhanced object** and the call that reads its implants (`ENHO_SOURCE_IS_ELSEWHERE`). On an `ENHO/XH` (class / interface enhancement) it answers empty **without** asking the structure (which dumps the server) and names the abapGit files that carry the methods. On a class or a program, `version` reads a **stored** version — `active`, `inactive`, or a number from the version history — and `compareTo` answers a **unified diff** between two, computed locally. Traps it holds (measured, `docs/adt-api-reference.md`): `?version=inactive` answers the active source when there is no inactive one, so the object document is asked first and the answer says *no inactive version*; a version is read from the link its history entry publishes, never built; `active` facing a number is read as `00000`, because the history regenerates that text. A version it could not read files `VERSION_NOT_READ`. `method` (a class, active or inactive) answers **one method**: `NAME`, `INTF~NAME`, or `LOCAL_CLASS->NAME`, sliced `METHOD … ENDMETHOD` from the include the class outline names, outline and source read in the same version. `textElements: true` adds the text symbols, selection texts and headings of a program or class; a category not read says so (`TEXT_ELEMENTS_NOT_READ`), never "none" |
| `adt_object_info` | Package, owner, dates, API state, structure | the answer is `object` (name, type, package, description, URI), `properties` (every attribute of the object document, its namespace dropped, dates in ISO 8601 UTC) and, for a class or interface, `elements`: the outline, each element with `at` and `implementationAt` as `{line, column, endLine, endColumn}` in the main source and its definition and implementation blocks the same way. a class enhancement or function-module interface enhancement (`ENHO/XH`, tools `CLASENH`/`FUGRENH`) has **no model in the ADT**: its own resource dumps the server (measured, 3 of 3), the enhanced object does not list it and the search index does not know the methods it adds. So the structure is **never asked**; the tool reads the one resource that answers (`objectproperties`, named route `objectProperties`: package chain, owner, API state, creation date), says `clasenh: true` with where the code really is (SE19; abapGit `<enho>.enho.xml` + `<enho>.enho.em_<method>.abap`) and files `CLASENH_NOT_IN_ADT` — never "no enhancement". On any other `ENHO/*` it answers `enhancedObject` (`kind` PROG/FUGR/CLAS/ENHO, name, URI kept percent-encoded); `null` on a BAdI implementation, which implements a spot, not an object — and for an `ENHO/XHB` the spot is read from the object's own body (`badi`: spot, BAdI definition, implementing class, referenced objects; one raw GET at the URI the search resolved, measured). On a package (`DEVC/K`) it answers `packagePath` (root first, via `findObjectPath`) and `parentPackage`; a failed path read says *NOT a root package*. On a service binding (`SRVB/SVB`) it answers `binding`: kind, UI or Web API, contract, and **per version** its release state, SRVD, `published`, service URL and entity sets with navigations, read from the binding and its detail without calling the service; a published version's URL names the `$metadata` route that reads it (V2 or V4, any namespace, V2 `;v=N`). A failed read files `BINDING_NOT_READ`, never "unpublished". For a class, interface, CDS view, table, data element or function module it also answers `apiRelease`, the **API release state the system holds**, per contract (C0–C4): state (`RELEASED`, `NOT_TO_BE_RELEASED`, `DEPRECATED`, …), usable in key-user apps and in cloud development, and the successors SAP names (`MARA` → `I_PRODUCT`, …); one GET on `/sap/bc/adt/apireleases/<uri>`. A read that failed is `read: false` and `API_RELEASE_NOT_READ`, never "not released". `abapLanguageVersion` (`standard`, `cloudDevelopment`, `keyUser`) comes from the object document it already reads |
| `adt_where_used` | Who calls this? | standard objects need `allowStandard: true`. The reply is a tree the ADT sends flattened (package folders, the using objects, the places of each use); the answer groups it back: `users`, one per using object, each with its `uses` (the section or method, its `usage` grades, its URI). Package folders are not users. The object itself appears with `self: true` when its own code names it, and `callers` counts the others. Users are paged (`max` 100 by default, up to 500; `offset` from `page.next.offset`), and `snippets: true` asks the code of the places of the page, each snippet tied to its place by `objectIdentifier` |
| `adt_package_tree` | What does this package contain? | `depth` up to 3 — `compact: true` drops the object list (hierarchy + counts only; a large root package at depth 3 is several MB otherwise) and allows up to 5. The sub-packages the depth did not reach are named (`DEPTH_LIMIT`, `subPackagesNotWalked`), and the objects of each package are paged (`max` 500, up to 5000, `next: {packageName, offset}`). The tree resource sends each row's short description **shifted to the next row** (measured, server-side, POST-only so not re-readable raw): it is returned as `treeDescription`, never as the row's description; `describe: true` reads the virtual folders of each package, **one POST that reads** (the IDE's project tree): every sub-package's correct description and `objectsBelow`, the objects under it. If that read fails, it falls back to one search per sub-package and files `PACKAGE_FOLDERS_NOT_READ` |
| `adt_clean_core_scan` | What do the CDS views of this package consume that is not released, and what should replace it? | `package` required; reads the package's DDLS from the system (one call each, `maxObjects` 1..300, default 100, sub-packages by default), extracts every data source and classifies it A/B/C/D against the catalogue, with the successor SAP names; an `entity` filter reads one source. `offset` reads the next page of sources (`scope.next.offset`); the findings are paged by `max` (default 200, at most 1000) and `findingsOffset`. `complete` is false, with each reason in `incomplete`, when an object was not read, a cap was reached, a sub-package was beyond the listing's depth or package cap, or the catalogue is partial; `absent` and `unmapped` list the names no catalogue classifies. Progress and cancellation supported |
| `adt_annotation_scan` | Which annotations reach this element and from **which layer** — and which elements have layers that contradict each other? | `package` required; reads the package's DDLS and DDLX from the system, then follows the upstream views they select from (`upstream`, default 20) — so a hide written in a **standard** view is seen too. Carries every annotation family, from the DDLX **and** from the inline DDLS. Answers what the **source** says; it knows nothing about switches, kernel layers or `IS_ACTIVE`, so every detector hit is a suspicion that `adt_annotation_chain` confirms at one ADT call. A finding is `ARMED` (hidden upstream, given a display role downstream, nothing holding it: the field does not render and no error is raised) or `HELD` (the same, with `@Metadata.ignorePropagatedAnnotations: true` holding the hide back: removing that line re-arms it); `hiddenKey` names which annotation hides it (`@UI.hidden` and `@Consumption.hidden` have different remedies), and `depth` the propagating hops, a deep row being matched on element name. A hide bound to a field is skipped as deliberate design, and an upstream view is read for its inline annotations only. The index is kept 10 minutes for follow-up lookups, the newest few packages at once (`refresh: true` rebuilds it; `scope.cached` says whether it was reused). Rows and findings are paged by `max` (default 200, at most 1000) and `rowsOffset`, the package sources by `offset`. A table answering 404 upstream is `notFound`, not a hole; a view not read, the `upstream` budget, the hop cap and an unparsed source each make `complete` false, with an entry in `incomplete` |
| `adt_value_help` | Which **released** value help CDS fits this field, and what do I bind? | candidates are filtered against the Clean Core catalogue **before** any ADT call; the entity's own source (read from the system) says which fields are already bound; every emitted key is validated against **this system's** annotation definitions (its DDLA) — if those cannot be read, the block says NOT VALIDATED; exposure is checked against the service definitions the system says use the entity (where-used, `maxServices` read, default 3, at most 20), and is conclusive only when every one was read; a call ceiling per run (`maxCalls`); the fields are paged by `maxFields` and `fieldsOffset`. A candidate past the budget, not read or not parsed stays `unverified` (never tier C), and each one, like a failed search or a precedent skipped for the budget, is an entry in `incomplete`; a proposed value help of your own is named by `valueHelp.namePattern`. The tiers rest on an observed rule: the annotation syntax is documented (ABAP Keyword Documentation 7.58), but SAP documents no semantics for `ObjectModel.dataCategory`, so a signal is evidence and never a guarantee. The recommended candidate's signals are on its row of `candidates`, and the catalogue is named by its file, not its path |
| `adt_annotation_chain` | Which annotation reached this element, and from where? | one GET on a single named route; reports the value that actually reaches the app per annotation, the source that contributed it, and any key written by more than one source or silenced entirely. Also flags the cross-key contradiction — hidden by one layer while another gives it a display role — which produces **no** conflict and is invisible to reading either source alone. Every active hide is listed (`hiders`), not only the first. The measured root with nothing under it is an empty chain, `complete: true` with `empty` saying that an element the entity does not have answers the same, and `next` naming `adt_object_info`. A reply that does not parse is `complete: false` with `PARSE_FAILED` and comes back verbatim, paged by `payloadOffset`. ⚠️ `entity` and `element` are disjoint scopes: an element-level defect is not visible in an entity-level call |
| `adt_contract_check` | Which OData expose aliases of this service are frozen contracts? | `service` required; reads the service definition (one call) and lists every alias with the EntitySet / EntityType it generates — the names a consumer addresses by hand and a rename breaks silently — plus an entity exposed under two aliases. With `apps` (at most 10 deployed UI5 apps, by BSP name), each app is read from the system's UI5 repository and every hand-written reference is checked against the **live** `$metadata` of the services its manifest names, V2 or V4, in the `sap` namespace or another one, and a V2 service at a version above 1 (`;v=N`). Checked: controller reads, function calls and their parameters, `$filter`/`$select` properties, absolute bindings, local annotation targets and paths, and manifest pages. A name the service no longer publishes is a `UI5_REFERENCE_BROKEN` finding, and each alias lists the files that cite it. The app's own `localService` copy is never used as a source. Apps are named, never searched, so an alias no named app cites is not claimed unused. Each part of an app not read (`notRead`: kind, name, code, reason) and each reference no service could judge is an entry in `incomplete`. CPI runs in another system |
| `adt_transport` | Which objects moved together, when, and by whom? | one GET on a named route, in one of two modes and never by default: `number` reads one request in full, `recent: true` reads the list the server offers. The answer is the **union of the request's own objects with every task's**, because a task's objects reach the request only when the task is released — with the per-task attribution kept. The list mode is **released only, last two weeks, no paging**: that is the server's scope, not a filter this tool applies, and it is returned as a structured `scope` field. It **names other developers**, because a request you hold a task in is listed under its owner. Local caps of 50 requests / 300 objects, applied after the bytes arrive, and always reported. With `keys: true` (detail mode only) it also answers **which ROWS moved** — the `E071K` table keys of each object, decoded field by field against the key layout the CTS declares, which was measured to be the DDIC's own. That is what turns `CDAT BUPAFLDMOD` from a maintenance-object name into the rows in the tables that actually travelled. One extra ADT call per object, so it is budgeted (25 by default) and every object it did not reach is counted in the answer. A key with `transported: true` is a row that moved; one without it is the key template of the object and moved nothing (an `ACGR` role answers 28 of those while `E071K` holds none). A 400 on one object means its keys were not resolvable for the carriers tried, never that it has none. Which objects are asked is the **system's own word**: `tm:obj_func` is `E071-OBJFUNC`, and its `K` means *has rows in the key list* (domain read) — every entry carries it decoded (`objFunc: {code, meaning, systemText}`), so a request that **deletes** an object (`D`) no longer reads like one that ships it, and every object in the key sweep says whether it was asked on the attribute, skipped on the attribute, or decided by the measured type census (`askedBy` / `skippedTypes[].by`). The third mode asks the **reverse** question: `object: {name, type}` reads the object's **version history** — every request that ever carried it, released or open, and the one **holding it now** (version `00000`). The feed's path is taken from the link `objectStructure` publishes, never assembled (a class keeps **five** histories, and three of the five undercount — the answer is their union); **transports of copies are set apart on the server's own `isTestTransport` flag**, never on a `"CP - "` title prefix (measured: most numbers in one class feed were copies). With `logs: true` (detail mode only) it also reads the request's **action log** (created, linked, released) and **transport log** (per system and step, each with its return code, and `highestReturnCode`); two more calls, and a log that failed says `read: false`. Beside the history, the object mode names the **open requests holding the object now** (`openRequests`, one more GET; empty means in no open request, never "never transported"). A fourth mode, `saved: true`, reads the list your **saved IDE search** selects (the Transport Organizer view: open and released requests): requests and tasks with an object count each, never the objects. The configuration is read, never created; without one the answer says `read: false`. The content of an old version is read by `adt_read_source` (`version`, `compareTo`), not here. On an `ENHO/XH` the object mode reads **nothing** of the history (its structure dumps the server), still names the open requests, and points at the caller of the added members. Lists are paged: `maxRequests` and `offset` (recent, saved), `maxObjectsPerRequest` and `objectsOffset` (number), `maxKeyLookups` and `keysOffset` (keys); an object whose keys were not read says why from a closed list (`400`, `budget`, `error`) with the carriers actually tried, and each cut, failed part or drift is an entry in `incomplete` |
| `adt_transport_routes` | Where does a request released here go? Which systems has the transport domain, which layer does each develop in, and what is the consolidation and delivery path per layer? | the STMS tables through the data preview, each with its field allowlist (`docs/security.md`, *The transport routes of the STMS*): `TCEVERS` for the versions, then of the chosen version `TCETRAL`/`TCETRALT` (layers), `TCESYST`/`TCESYSTT` (systems and their development layer), `TCERELE` (consolidation) and `TCEDELI` (delivery), and the domain from `TMSCDOM`/`TMSCSYS` -- about nine calls, no route of its own, no function module. The active version is the one row with `ACTIVE = A` (measured); none or several is `NOT_READ` and asks for `version`, never a guess. `chains` gives per layer the systems a request travels: the integration system, its consolidation target, then every active delivery route, each system once. `ORICON` and the delivery columns are passed through as read (their meaning is not measured). A table not read is `NOT_READ` with `TRANSPORT_ROUTES_NOT_READ`, never an empty route |
| `adt_runtime_errors` | What dumped (ST22), where, on which line -- and what the gateway logged | the Eclipse **Feed Reader** over the wire: `feeds: true` reads the catalogue `/sap/bc/adt/feeds` (the feeds the system offers, each with the attributes and operators a filter may use); `list: {feed: "dumps"\|"gateway"\|"atc", filters?, max?, skip?, report?}` reads one page (`$top` 1..100, default 50) of `/sap/bc/adt/runtime/dumps`, `/sap/bc/adt/gw/errorlog` or `/sap/bc/adt/atc/feeds/verdicts`; a dumps page also answers `groups`: its dumps grouped by runtime error and program (and the failing line with `report: true`), with count, first and last time and ids -- this page only, never the whole of ST22; `detail: {id, full?}` returns ONE dump -- header, what happened, error analysis, where terminated, source extract with the failing line marked, call stack with the ADT position of each frame (all parsed from the entry, which **carries its whole report**, about 17 KB), plus the dump **resource** at the HTTP twin of the entry's `self` link (`/sap/bc/adt/runtime/dump/<key>`: links and the 20-chapter index with line numbers) and, with `full: true`, the whole ST22 report as text, chosen variables included. `filters` is up to two `{attribute, op, value}` triples **generated** into the catalogue's own prefix grammar, comma form (`and ( equals ( user , X ) , notContains ( objectName , Y ) )`, measured to filter); free text never reaches `$query`, the route regex is a second fence, and the side-by-side form -- which **dumped the server** when it was probed -- is never produced. The gateway log and the ATC feed answered no entry when measured: their entries come back generic and flagged `entriesMeasured: false`. A full page is `SERVER_PAGE_FULL` with `next.skip` (the server gives no total), the server's own window is `serverWindow.from`, and a dump resource or formatted report not read is an entry in `incomplete`. The answer names whoever dumped (that is the question); the audit line carries the feed, the page and the dump's timestamp+host+sequence, never a user. And **every** tool uses the same feed after an HTTP 500: the newest dump of the session's user since the call is appended to the error (`-- the SAP system dumped: <error> in <program> (ST22 <key>; …)`) and filed as `SERVER_DUMPED`, because on every measurement a 500 from the ADT was a dump |
| `adt_atc_run` | Does this object pass the check variants -- Clean Core governance, development practices, SAP's DEFAULT -- and if not, which finding, which check, which line? | the **second POST** this server sends, and the first that leaves something on the server: an ATC result worklist per variant (what the ATC Result Browser lists), nothing else -- no lock, no transport, no object touched (measured). `variants`: up to **3** from the closed set of SAP's `DEFAULT`, the system check variant (read from `atc/customizing` at start) and the variants your installation lists (`npm run config -- atc add`), run one after the other on the same object; default the system check variant, or `atc.defaultVariant` when set. Per variant: `POST /sap/bc/adt/atc/worklists?checkVariant=<v>`, `POST /sap/bc/adt/atc/runs?worklistId=<id>` with a body **generated** from one validated object URI and `maxFindings` 1..100, then `GET /sap/bc/adt/atc/worklists/<id>`. The set is closed because **the server hands an id to any name** (measured); an `ENHO/XH` is refused (its URI dumps the server). The answer: each finding's priority, check, message, source position, quickfix flags, documentation link; with several variants, one block per variant, and a variant that failed is listed as **not run** -- never clean. After each run the variant itself is read once (`atcCheckVariant`): a variant created in the ADT (`CHKV`) answers `variantChecks`, its checks with their parameter values; a variant created in transaction SCI, which SAP documents the ADT cannot display, answers `variantKind: SCI` with that note. A short list says why (`truncatedBy`: `maxFindings`, or `worklist` when the worklist holds fewer findings than the run counted), run stats that are not three integers are `PARSE_FAILED`, and the exempted findings listed are counted. A few seconds per variant. `ATC_NOT_RUN` / `ATC_RESULT_NOT_READ` / `ATC_SYSTEM_VARIANT_NOT_READ` / `ATC_VARIANT_NOT_READ` in the journal. ABAP Unit stays with the IDE; exemptions are governance writes and are not admitted |
| `adt_customizing` | Which pricing-procedure step calls routine 953? Which copy control carries requirement 653? | the **first POST** this server sends: `/sap/bc/adt/datapreview/freestyle`, body a `SELECT` **generated** from a closed grammar (one table, listed fields, `=`/`<>`/`IN`/`LIKE` joined by `AND`, 1..200 rows; `LIKE` takes a name with `*` wildcards and the module writes the literal and its `ESCAPE`; a table may fix the columns it admits, so a user field is never read) for a table in the closed list `CUSTOMIZING_TABLES` — the SAP-standard tables in [`data/defaults/customizing-tables.json`](../data/defaults/customizing-tables.json) (pricing procedures and condition tables, copy control, the VOFM registry, launchpad semantic objects, the object directory, CDS header annotations, payment terms, STVARV parameters, partner determination, the material master screen map, MRP areas, material status, the factory calendar, the organizational units, application log objects, Code Inspector check variants) **plus the tables your installation added** with `npm run config -- table add`, through the same validation. Any other table, field or value the grammar cannot say is refused **before a socket opens**; the server would answer any table (`VBAK` measured 200), so the fence is the client and it is tested. Read-only by semantics (no lock, no transport; `SM12` checked before and after), POST by wire. `totalRows` is the server's count **without** the cap; NUMC columns compare at full width (`0000953` in `T683S`, `953` in `TVCPA`). The audit line carries the table and the row cap, never a row. `runQuery`/`tableContents` of the library stay denied — the decision, dated, is in `docs/security.md` |
| `adt_launchpad` | Which tiles and target mappings does catalog X carry, which groups show them, which catalogs does role Y get, and is the semantic object registered? | one `kind` per call (`catalogs`/`catalog`, `groups`/`group`, `spaces`/`space`, `pages`/`page`, `semobjs`/`semobj`, `roleCatalogs`). The one place the routes leave `/sap/bc/adt`, for **SAP-standard services only**: OData V2 under four `ODATA_ROOTS` (PAGE_BUILDER_CONF/CUST, FDM_*_CUST_SRV; never `PAGE_BUILDER_PERS`, `$batch` or a generic GET over entity sets). No customer (Z) service is called, and every person-like key is stripped from every body. `semobjs`/`semobj` read the `/UI2/SEMOBJ*` tables through the ADT data preview, as `adt_customizing` does. Decision, dated, in `docs/security.md` (*The Fiori launchpad*); shapes in `docs/adt-api-reference.md` |
| `adt_syntax_check` | Does the source the system stores for this class, program, behaviour definition, CDS view or metadata extension compile — the active version, or the inactive one waiting to be activated? | the **fourth POST** this server sends: `/sap/bc/adt/checkruns?reporters=abapCheckRun`, a body built from one object URI (class, program, behaviour definition, CDS view, metadata extension) and the version, **no source sent** — the server checks what it stores. Each message: type, text, include, line, column. Measured: no `Location`, no run id, nothing left on the server, a stateless session (the IDE runs the same check after every save). `version: inactive` first reads the object document, because on an object with **no** inactive version the server checks an empty source and reports an error that is not in the program (measured); the answer then says *no inactive version* and nothing is sent. | `adt_package_health` | How healthy is this package for Clean Core, in one answer? | a composition, no read of its own: the package is listed **once**, then the Clean Core scan of its CDS views (the same run as `adt_clean_core_scan`: levels and the first `maxFindings` findings, default 20, at most 200) and the syntax check of the stored **active** version of each class, program, behaviour definition and metadata extension (the same check run as `adt_syntax_check`, `maxChecks` 1..50, default 20; `checksOffset` checks the next page). `complete` is true only when every part read everything, with each reason in `incomplete`; source types no part checks (interfaces, function groups, includes) are counted in `notCovered`: an object not checked, a view not read or a cap reached makes it false, and nothing is summarised about what was not read. Without the catalogue the Clean Core part says it did not run and the syntax part still runs. With `atc: true` it also runs the **ATC once over the whole package** (the default variant; the package as one virtual-folders object reference, as the IDE sends it), leaving a result worklist like `adt_atc_run`, and counting the objects the run checked (`objectsChecked`: a run over no object is incomplete, never a clean package); without it the answer says ATC was not asked |
| `adt_find_definition` | Where is the symbol at this line and column of a class defined? | the IDE's F3: `POST /sap/bc/adt/navigation/target?uri=<source#start=l,c>&filter=definition` with the class's **stored active main source as the body** (read first through the guarded client, never text from the caller). The answer is the target's source URI, object URI, line and column, the object it lands in (`name`, `type`, from its URI), and whether it is in the same class; "named none" when the server resolves nothing at the position; every reference the reply names is listed (`targetCount`, `targets`). Classes only (the one family measured); an unsaved editor buffer is not seen |
| `adt_used_objects` | What does this class use, and is each of those objects released? | the IDE's Relation Explorer, "Used Objects": `POST /sap/bc/adt/objectrelations/network` with a body naming the class and **nothing else** (no source), one level deep. **Every** used object is listed with type, package, **package path** and whether it is in another package; then the **API release state** of each class, interface, CDS view, table, data element and function module, one GET each, at most 25 (`maxReleaseReads`). An object whose state was not read (past the cap, a family not measured, a failed read, a reply that does not parse, a use listed without a URI) is named in `notRead` with its code and reason and makes `complete` false; the counts cover only what was read, and `releaseOffset` reads the next page of release states. With `boundary: true` it also describes each use into another package by what **both sides declare**: the use accesses of the class's package that relate to it, and whether the used package is encapsulated and which interfaces it publishes (package documents, at most 11). **Never a verdict**: which objects an interface exposes is not readable over ADT, and whether the system enforces the package check is not read. Classes only (the one family measured); for a CDS view, `adt_clean_core_scan` |

`adt_read_source` answers a second question the working tree cannot: **who implanted code
into this standard object.** With `enhancements: true` it lists the enhancement
implementations bound to the source — the ENHO, the enhancement-point path, whether the
implementation *replaces* that point, the line it sits at, and the stored state (on, stand-by,
off) of the Switch Framework switch its package hangs on, because the system lists an
implementation whether or not its switch is on — and with
`enhancementSource: true` the implanted source itself. An implicit enhancement or an
enhancement spot implementation never appears in a Z-namespace sweep, and no abapGit
repository serialises it against the standard object it modifies. When the read fails, the
footer says so — *"enhancements NOT read"* is never rendered as *"there are none"*.

`adt_value_help` is the one tool that is a pipeline rather than a call. For each field of a
CDS view it resolves the data element and the domain in the system (a projection field
inherits its type, so the source text cannot answer this), builds candidates from the released
catalogue, classifies them **A / B / C with the evidence** instead of asserting a rule, refuses
annotation keys that are not released in this release, and checks that the entity is exposed in
the service definition — an omission that makes the F4 come up empty with no activation error
and no `/IWFND/ERROR_LOG` entry.

The strongest signal is not a name at all: a field whose **DDIC type** is `UNIT`, `CUKY` or
`LANG` *is* a unit key, a currency key or a language key, whatever it is called, and that
costs nothing extra because the field list already carries the type. It is also the only
signal of the type that survives a projection, where the field restates neither its type
nor its annotations. The **semantic annotations the system resolves** come with the same field
list, at no extra call, inherited ones included: a quantity's
`@Semantics.quantity.unitOfMeasure` names its unit field even when the projection's source says
nothing. `BaseUnit` is the case the tool was built for: its data element states
`BASEUOM` (measured — not `UNIT_OF_MEASURE`, which is what it looks like), nothing named
`BaseUnit`, `BASEUOM` or `MEINS` is in the catalogue, and its type `UNIT` lands straight on
`I_UnitOfMeasureStdVH`. `readAnnotations: true` additionally reads the entity's own source
for `@Semantics`; what the system resolves wins over what the file writes.

When nothing matches by name or by type it **asks the system** rather than guessing: an
anchored, type-filtered repository search on the concept (one call, ~3 KB), and if that
comes back empty, the domain's value table through where-used — the only route that can
discover that the VDM calls the concept something else entirely (`T006` is what connects
`MEINS` to `UnitOfMeasure`). Everything the search finds still passes the release gate, and
when nothing is confirmed the proposed own view keeps a **placeholder** source instead of
naming an entity that may not exist. Turn it off with `deepSearch: false`.

With `precedent: true` it also asks who else binds the recommended value help, reads one such
consumer from the system and copies its `additionalBinding` — cited, never invented.

The catalogue is **both** files, not just the release info: hundreds of CDS entities exist only
in `objectClassifications_SAP.json` as `classicAPI`, so loading one file would answer "unknown
to the catalogue" for entities that exist and are classified. They are still never recommended —
Level B is not a Level A answer — but they are shown as rejected candidates with their state and,
when the catalogue names one, with their released successor.
